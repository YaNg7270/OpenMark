# 软件工程实践

软件工程关注的是如何让软件在长期演化中保持可维护。它承认一个基本事实：需求会变，人员会流动，因此衡量设计好坏的标准不是当下写得快不快，而是半年后改起来难不难。

## 需求分析

需求分析的目标是把模糊的期望转化为可验证的陈述。可验证是关键，因为它决定了验收能否有客观标准。

- 功能性需求描述系统应当做什么。
- 非功能性需求描述系统应当做到什么程度，例如延迟、并发与可用性。
- 约束条件描述不可协商的边界，例如合规与既有技术栈。

| 需求类型 | 表述方式 | 验收方式 |
| --- | --- | --- |
| 功能性 | 给定条件与操作，产生预期结果 | 用例测试 |
| 性能 | 在指定负载下的量化指标 | 基准测试 |
| 可用性 | 时间窗口内的可用比例 | 监控统计 |

把目标写成可测指标，能提前暴露分歧。若两个利益相关者对同一需求的理解不同，书面化的过程本身就是最有价值的产出。

> 需求变更不是异常，而是常态。设计的核心任务之一，就是让未来的变更尽量局限在局部，而不是牵动全局。

## 版本控制

版本控制记录代码的演化历史，使协作与回退成为可能。

1. 提交应当原子且语义完整，一次提交只解决一件事。
2. 分支应当短命，长期分支的合并成本会随分歧累积而急剧上升。
3. 提交信息应当解释动机，而不只是复述改动内容。

集中式与分布式模型的主要差别在于历史的存放位置。分布式模型下每个副本都持有完整历史，因此离线提交与本地分支变得自然，但也带来历史被随意改写的风险，需要靠约定加以约束。

代码评审是版本控制流程中最有价值的环节之一。它的收益不仅是发现缺陷，更在于知识的扩散与规范的自然形成。评审意见应当聚焦可执行的问题，而不是个人风格偏好。

## 持续集成与交付

持续集成要求团队成员频繁把改动合并到主干，并用自动化手段验证每次合并。

- 构建应当可重复，同样输入必须得到同样输出。
- 测试应当快速分层，单元测试保证秒级反馈，端到端测试覆盖关键路径。
- 流水线失败必须优先修复，红着的流水线会迅速失去公信力。

持续交付在持续集成之上进一步要求主干始终处于可发布状态，部署成为例行操作而非特殊事件。这需要配套的回滚机制、特性开关与渐进式发布策略。

最后要记住，工具只能降低协作成本，不能替代工程判断。一个测试很全但设计混乱的项目，依然会在需求变化面前迅速失速；而一个设计清晰但缺乏自动化的项目，则会在人员更替中悄悄积累风险。
