# React 状态管理：单向数据流、受控组件与并发渲染

在 React 里谈状态管理，绕不开单向数据流（one-way data flow）这条主线。state 永远向下流动，事件永远向上冒泡，任何一个组件看到的都只是当前这次 render 的快照，而不是一个随时可变的全局对象。理解这一点，很多「为什么 UI 没更新」的困惑会自然消失。

## 受控与非受控

受控组件（controlled component）把表单值交给 React state 托管，每次输入都要经过 onChange 再回写；非受控组件（uncontrolled component）则把值留在 DOM 里，用 ref 读取。

- 受控组件胜在可预测，任何一次输入都能被拦截、校验、格式化；
- 非受控组件胜在代码少，迁移旧表单或集成第三方库时更省事；
- 二者混用时要特别小心，否则会出现两个真相源（source of truth）。

## 批处理与快照

React 会把同一个事件回调里的多次 setState 合并成一次批处理（batching），因此连续调用不会触发多次渲染。

```ts
function handle() {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
  // 两次都基于最新的 c，最终加 2
}
```

如果直接写 `setCount(count + 1)` 两次，由于闭包捕获的是同一次渲染里的 count，结果只会加 1。函数式更新（functional update）正是为了解决这种陈旧闭包问题。

| 写法 | 是否安全 | 原因 |
| --- | --- | --- |
| setCount(count + 1) | 否 | 依赖旧闭包 |
| setCount(c => c + 1) | 是 | 读取最新值 |

## 并发渲染

并发渲染（concurrent rendering）引入了可中断的渲染过程。transition 与 useDeferredValue 允许把非紧急更新标记为低优先级，从而让高优先级的输入始终保持流畅。

> 并发不是多线程，它只是把「一次渲染」拆成可暂停、可放弃的若干片段。

副作用（side effect）必须放进 useEffect 或事件处理器，绝不能在渲染阶段触发，因为渲染可能会被丢弃或重放。依赖数组要如实列出所有被读取的外部变量，否则很容易读到过期值。对于跨组件共享的高频状态，可以考虑外置 store，再用 selector 精确订阅，避免整棵子树跟着一起重渲染。

## 状态库的边界

引入外部状态库之前，先问清楚它解决的问题属于哪一类：是跨组件共享，还是异步缓存，抑或只是为了免去层层透传。Redux 适合可预测的全局状态与时间旅行调试，Zustand 这类轻量方案则更适合中小型应用。

- 能用局部 state 解决的，就不要升级成全局 store；
- 只有真正被多方订阅的数据才值得下沉；
- 库本身并不会替你决定数据的所有权。

## 小结

状态管理的难点不在 API，而在于判断「这份数据到底该由谁拥有」。把所有权想清楚，受控、批处理、并发这些机制才会各就各位。
