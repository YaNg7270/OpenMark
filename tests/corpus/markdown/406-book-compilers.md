# Chapter 7 — 编译原理：从源文本到优化后的中间表示

编译器 compiler 本质上是一条流水线：把 source language 的文本转换成 target
machine 能执行的指令，中间要经过若干次 representation 的变换。本章沿着这条流水线
展开：先讲词法分析 lexing（§1）与语法分析 parsing（§2），再引入中间表示 IR（§3），
然后进入最有趣的部分——优化 optimization（§4），最后在 §5 讨论代码生成 code
generation 与后端。本章小结与练习位于末尾。

## 1. 词法分析 Lexical Analysis

### 1.1 任务与接口

Lexer 的输入是字符流，输出是 token 流。每个 token 携带类型与词素 lexeme：

```
input:  let x = 3 + y;
tokens: (LET,"let") (ID,"x") (EQ,"=") (NUM,"3") (PLUS,"+") (ID,"y") (SEMI,";")
```

Lexer 通常还要维护一个 symbol table，记录每个标识符出现的位置，供后续阶段解析作用域。

### 1.2 正则表达式与有限自动机

词法规则用 regular expression 描述，因为正则恰好刻画了实现 lexer 所需的计算能力。
一个标识符可以写成

$$
\text{id} = [a\text{-}zA\text{-}Z\_][a\text{-}zA\text{-}Z0\text{-}9\_]^{*}.
$$

数字常量可以写成

$$
\text{num} = [0\text{-}9]^{+} \; (\text{.}\,[0\text{-}9]^{+})?
\; (\text{[eE]}\,[\text{+}\text{-}]?\,[0\text{-}9]^{+})? .
$$

每个正则都可以机械地转换为 NFA，再子集构造为 DFA。DFA 的优点是识别一个字符只需要
一次状态转移，即 $O(1)$ 摊还时间；缺点是有时状态数会指数爆炸，因此实际 lexer 常用
NFA 模拟加缓存。

### 1.3 最长匹配与优先级

当多条规则都能匹配时，lexer 采用两条准则：第一，取最长匹配（maximal munch）；
第二，长度相同时取规则书写顺序靠前者。`==` 会被优先识别为等号而不是两个赋值号，
正是因为最长匹配。编程语言里 `a+++b` 的解析结果，也直接由这条规则决定。

| 目标 | 常用形式 | 实现方式 |
| ---- | -------- | -------- |
| 标识符 | 正则 | DFA |
| 数字 | 正则 | DFA |
| 字符串 | 正则（含转义） | DFA |
| 注释 | 正则 | 特殊处理嵌套 |

### 1.4 手写 Lexer 的实现

生产级 lexer 很少真的生成整张 DFA 表，而是用状态机代码加最长匹配缓存。下面是一个
把标识符与整数都识别出来的极简实现：

```python
def lex(src):
    i, tokens = 0, []
    while i < len(src):
        c = src[i]
        if c.isalpha() or c == '_':
            j = i
            while j < len(src) and (src[j].isalnum() or src[j] == '_'):
                j += 1
            tokens.append(('ID', src[i:j]))
            i = j
        elif c.isdigit():
            j = i
            while j < len(src) and src[j].isdigit():
                j += 1
            tokens.append(('NUM', src[i:j]))
            i = j
        elif c.isspace():
            i += 1
        else:
            tokens.append(('OP', c))
            i += 1
    return tokens
```

这段代码体现了两个工程要点：第一，识别标识符时一路读到非标识符字符再提交，正是
最长匹配；第二，空白字符在这里直接跳过，但真正的编译器要记录行列号，以便报错时
给出准确位置。参见 §1.3，最长匹配与规则优先级是所有这类实现共有的两条准则。

## 2. 语法分析 Parsing

### 2.1 上下文无关文法 CFG

Syntax 用 context-free grammar 描述。一个 CFG 由四元组 $G = (V, \Sigma, R, S)$ 构成：
$V$ 是非终结符集合，$\Sigma$ 是终结符集合，$R$ 是产生式集合，$S$ 是开始符号。例如
一个极简表达式文法：

```
E -> E + T | T
T -> T * F | F
F -> ( E ) | id
```

这个文法是有歧义的：表达式 `id + id * id` 存在两棵不同的 parse tree，一棵认为
乘法优先，另一棵认为加法优先。歧义是语法设计的大敌，必须通过重写文法或引入
优先级声明来消除。

### 2.2 推导、左递归与消除

从 $S$ 出发反复替换非终结符，得到终结符串的过程叫推导 derivation。上面的 $E$ 与
$T$ 规则存在**直接左递归** $E \to E + T$，它会让递归下降解析器无限递归。消除左递归
的标准手法是引入新非终结符，把左递归改写成右递归：

```
E  -> T E'
E' -> + T E' | ε
```

改写后文法识别的语言完全相同，但不再左递归，适合 LL(1) 分析。

### 2.3 LL 与 LR

- **LL(k)** 解析器从左到右读输入，构造最左推导，需要预测分析表。它实现简单，错误
  恢复友好，但无法处理左递归，表达力受限。
- **LR(k)** 解析器从左到右读输入，构造最右推导的逆过程，使用状态栈与归约动作。
  它能处理几乎所有实际编程语言的文法，且不需要改写左递归，代价是分析表更大、
  错误信息更难理解。

| 特性 | LL(1) | LR(1) / LALR(1) |
| ---- | ----- | --------------- |
| 方向 | 最左推导 | 最右推导（逆） |
| 左递归 | 需消除 | 允许 |
| 分析表 | $O(\|V\|\|\Sigma\|)$ | 状态数较多 |
| 实现难度 | 低 | 高 |
| 典型工具 | 手写递归下降 | yacc / bison |

```python
def parse_expr(tokens):
    # E -> T E' ; E' -> '+' T E' | eps
    node = parse_term(tokens)
    while peek(tokens) == '+':
        consume(tokens, '+')
        node = ('add', node, parse_term(tokens))
    return node
```

上面的递归下降函数把左递归消除后的文法直接翻译成代码，结构清晰，是手工编写
解析器最常用的方式。参见 §2.2 的改写规则，二者一一对应。

## 3. 中间表示 Intermediate Representation

### 3.1 为什么要 IR

Source 与 target 之间的直接翻译会让前端与后端紧紧耦合：支持 $m$ 种源语言与 $n$
种目标机器需要 $m \times n$ 个编译器。引入统一的 IR 后，只需 $m$ 个前端与 $n$ 个
后端，这是编译器工程中最重要的解耦。

### 3.2 三地址码与 SSA

三地址码把每个运算限制成「一个操作符、两个源、一个目标」，因此指令短小、易于
分析与重排。对 `a = b*b - 4*a*c`，可以生成

```
t0 = b * b
t1 = 4 * a
t2 = t1 * c
t3 = t0 - t2
a  = t3
```

SSA（static single assignment）在此基础上要求每个变量只被赋值一次，赋值多次时用
新名字。这让 def-use 关系变成显式的边，数据流分析几乎免费：

```
t0 = b * b
t1 = 4 * a
t2 = t1 * c
t3 = t0 - t2
```

在 SSA 下，`t3` 的两个来源一目了然，常量传播与死代码消除都可以直接顺着边进行。
遇到控制流汇合点用 $\phi$ 函数合并不同路径的值：

```
x = φ(x1, x2)
```

### 3.3 基本块与控制流图

IR 生成之后通常先把它切分成基本块：一段只有单一入口、单一出口、内部不发生跳转的
线性指令序列。块与块之间用有向边连接，得到控制流图（CFG）。绝大多数数据流分析都
在 CFG 上进行，而不是在原始指令列表上进行，因为块内的顺序是确定的，块间才需要
合并信息。

```text
      ┌───────────┐
      │ B0: 入口   │
      └─────┬─────┘
      cond  │
      ┌─────┴─────┐
      ▼           ▼
 ┌────────┐  ┌────────┐
 │ B1: 真  │  │ B2: 假  │
 └────┬───┘  └────┬───┘
      └─────┬─────┘
            ▼
      ┌───────────┐
      │ B3: 汇合   │
      └───────────┘
```

汇合点正是 §3.2 里 $\phi$ 函数出现的地方：不同路径带来不同版本的值，$\phi$ 负责
把它们合并成一个新名字。

## 4. 优化 Optimization

优化必须在**保持语义**的前提下改善某个目标（运行时间、代码大小或能耗）。绝大多数
优化是局部规则加全局数据流分析的组合。

### 4.1 常量折叠与传播

常量折叠在编译期直接算出结果：`3 + 4` 变成 `7`。常量传播把已知常量代入使用点：

```
a = 5
b = a * 2   ->   b = 10
```

两者通常联动，折叠产生的常量继续传播，触发新一轮折叠，直到不动点。

### 4.2 公共子表达式消除

若两个表达式在到达各自使用点之间没有任何操作数被重定义，它们就是公共子表达式，
可以只算一次。在 SSA 形式下这一步几乎是免费的，因为重复的表达式名字相同。

### 4.3 活跃变量分析与寄存器分配

一个变量在程序点 $p$ 活跃，当且仅当它在 $p$ 之后会被使用而中间未被重定义。活跃
变量分析是反向数据流分析，转移函数为

$$
\text{Live\_out}(B) = \bigcup_{S \in \text{succ}(B)} \text{Live\_in}(S),
$$

$$
\text{Live\_in}(B) = \text{Use}(B) \cup
\bigl(\text{Live\_out}(B) \setminus \text{Def}(B)\bigr).
$$

分析结果就是 interference graph：同时活跃的两个变量不能共用寄存器。给这张图上色，
颜色数不超过可用寄存器数就意味着无需溢出 spill。图着色是 NP 完全的，因此实现上
通常用 Chaitin–Briggs 的启发式：先合并可合并的节点，再反复简化低度数节点。

### 4.4 循环优化

循环是热点的同义词，因此大多数优化都围绕它展开：

- **循环不变量外提**：把循环体内不随迭代改变的计算移到循环外。
- **强度削弱**：把昂贵的乘法替换为等价的加法，例如 `i*4` 用指针自增代替。
- **循环展开**：复制循环体以减少分支与索引开销，代价是代码膨胀。
- **循环交换与分块**：改善多维数组的 cache 局部性。

```text
原始:                        外提后:
for i in 0..n:               t = x + y
    a[i] = (x + y) * i       for i in 0..n:
                                 a[i] = t * i
```

### 4.5 优化的顺序与不动点

优化之间有相互作用：常量传播可能开启死代码消除，死代码消除又可能让某个分支
条件变成常量，从而开启进一步的传播。因此优化通常在一张 pass 图上迭代，直到达到
不动点或预算耗尽。这也是为什么「编译很久」的代码往往运行很快——时间花在了反复
分析上。

> 一条实用经验：先做会暴露其他机会的优化（内联、常量传播），再做清理型优化
> （死代码消除、公共子表达式消除），最后做面向机器的优化（寄存器分配、指令调度）。

### 4.6 内联与逃逸分析

**内联**（inlining）把被调用函数的函数体直接展开到调用点。它本身很少是最终目标，
它的副产品才重要：内联之后常量参数可以被传播，边界完全消失，后续优化才有机会
生效。代价是代码膨胀，因此启发式只内联热点或小函数。

**逃逸分析**判断一个对象是否会「逃出」当前函数或线程。若对象的地址从不逃逸，
编译器就可以把它分配在栈上甚至打散成寄存器变量，省下一次堆分配以及随之而来的
垃圾回收压力。在 JIT 环境里，逃逸分析还能触发标量替换与锁消除，收益常常超过
所有算术优化的总和。

## 5. 代码生成与后端 Code Generation

### 5.1 指令选择

从 IR 到目标指令涉及指令选择，本质是在目标机器的指令集合上覆盖 IR 的表达式树。
代价模型按指令的周期数加权，动态规划求解最小的覆盖代价。这是经典的树覆盖问题。

### 5.2 指令调度与寄存器分配

指令调度重排指令顺序以隐藏流水线延迟，同时必须尊重数据依赖。寄存器分配把虚拟
寄存器映射到物理寄存器，前面 §4.3 的 interference graph 就在这里派上用场。
JIT 编译器还会做去优化 deoptimization：当某个假设被打破（比如类型改变），回退
到未优化版本，从而兼顾峰值性能与动态类型的灵活性。

### 5.3 一个完整的后端顺序

| 阶段 | 输入 | 输出 | 关键算法 |
| ---- | ---- | ---- | -------- |
| 指令选择 | 线性 IR | 机器 IR | 树覆盖 / 动态规划 |
| 指令调度 | 机器 IR | 调度后 IR | 列表调度 |
| 寄存器分配 | 调度后 IR | 物理寄存器 | 图着色 |
| 窥孔优化 | 汇编 | 汇编 | 局部模式匹配 |

### 5.4 窥孔优化的一个例子

窥孔优化在局部窗口内做模式替换，实现简单、收益稳定。一个经典例子是消去多余的
加载与存储：

```text
原始:                        优化后:
load  r1, [a]                load  r1, [a]
store r1, [b]                store r1, [b]
load  r2, [b]                mov   r2, r1
mov   r3, r2
```

由于 `load r2, [b]` 读到的正是刚刚写进去的值，编译器可以直接复用寄存器 `r1`，
省掉一次内存访问。这类优化的正确性依赖对别名关系的精确判断：只要 `a` 与 `b`
可能指向同一地址，就不能随意重排。这也解释了为什么 §4 的数据流分析必须先于
窥孔优化运行——没有别名信息，局部替换就是在赌博。

## 6. 本章小结 Summary

本章走完了编译器的经典流水线。§1 用正则与有限自动机刻画词法分析，并给出最长匹配
与优先级两条判定规则；§2 引入上下文无关文法、推导与左递归消除，对比 LL 与 LR 的
代价；§3 说明 IR 解耦前端与后端，重点介绍三地址码与 SSA；§4 系统讨论优化，从常量
折叠、公共子表达式消除，到活跃变量分析、寄存器分配与循环优化；§5 覆盖指令选择、
调度与窥孔优化。到此，一条从字符到指令的完整路径已经铺开。
