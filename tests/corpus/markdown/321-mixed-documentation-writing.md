# 技术写作：结构化写作、术语一致与示例驱动

技术写作（technical writing）的第一读者其实是三个月后的自己。文档写不好，往往不是因为词穷，而是因为结构混乱、术语飘忽、缺乏可运行的示例。把握住这三点，文档质量就能稳定在一个不低的水平上。

## 结构化写作

结构化（structured writing）要求读者能在几秒内判断「这篇文档是否解决我的问题」。因此开篇必须先说清楚适用范围与前置条件，再进入细节。

- 把「是什么、为什么、怎么做」按顺序拆开，不要混在一段里；
- 每节只讲一件事，标题用动宾结构而非名词堆砌；
- 长文要给出目录，让读者可以跳读。

| 结构 | 作用 | 常见写法 |
| --- | --- | --- |
| 概述 | 建立上下文 | 一段话说清目的 |
| 前置条件 | 避免中途卡壳 | 列表列出依赖 |
| 步骤 | 指导操作 | 有序列表 |
| 参考 | 供查阅 | 表格或词典 |

## 术语一致

术语一致（terminology consistency）看似小事，却直接决定读者会不会在脑中不断做映射。

> 同一个概念只用一个词，同一个词只指一个概念。

如果正文里「节点」和「实例」混用，读者会怀疑它们是两个不同的东西。解决办法是维护一份术语表（glossary），并在评审时把它当作硬性检查项。对外来术语要统一处理：要么统一保留英文原词，要么统一给出中文译名，切勿随机切换。缩写首次出现时给出全称，之后才能放心使用。

## 示例驱动

示例驱动（example-driven）的文档最好用：先给一个能跑起来的最小例子，再逐步扩展。

```ts
// 最小可运行示例：发起一次请求
const res = await fetch("/api/health");
if (!res.ok) {
  throw new Error("request failed: " + res.status);
}
console.log(await res.json());
```

示例要满足几个条件：可直接复制粘贴、输出明确、边界条件有所交代。反面教材是伪代码——它看似简洁，却把读者最需要确认的细节（错误处理、参数顺序）全部省略掉了。

1. 给出最短的 happy path；
2. 补充常见错误的排查方法；
3. 最后才谈高级配置与性能调优。

## 简洁与准确

写作时要主动删掉「非常」「显然」「简单地」这类虚词，因为它们既不增加信息，也容易让读者在卡住时感到被冒犯。被动语态能免则免，每句话尽量让动作的主体明确出现。版本相关的说明一定要标注适用的版本号，否则半年后读者无法判断这段内容是否仍然有效。

## 小结

结构决定可读性，术语决定准确性，示例决定可信度。把这三条当作写作清单，文档就会从「写完」走向「好用」。
