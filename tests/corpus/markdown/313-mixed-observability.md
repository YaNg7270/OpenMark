# 可观测性：指标、日志与链路追踪

可观测性（observability）常被简化成「三件套」——metrics、logs、traces。这个说法并不错，但真正决定一套系统能否被观测的，不是采集了多少数据，而是这些数据能否回答「线上现在到底发生了什么」。

## 指标

指标（metric）是聚合后的数值时间序列，适合看趋势与告警。常见的四类黄金信号是延迟（latency）、流量（traffic）、错误（errors）和饱和度（saturation）。

- 计数器（counter）只增不减，用于统计请求总数；
- 计量器（gauge）可升可降，用于表示队列深度、连接数；
- 直方图（histogram）用于记录分布的延迟桶。

| 类型 | 单调性 | 典型用途 |
| --- | --- | --- |
| counter | 单调递增 | 请求计数 |
| gauge | 可升可降 | 内存占用 |
| histogram | 分桶统计 | P99 延迟 |

聚合指标时务必保留标签（label），否则一旦出问题就无法按服务、实例或版本下钻。

## 日志

日志（log）是离散事件记录，优势在于细节丰富，劣势在于体积巨大且难以聚合。结构化日志（structured logging）把每条记录写成带字段的 JSON，让检索与统计成为可能。

> 日志的关键不是写得多，而是写得可被查询、可被关联。

```json
{"level":"error","service":"checkout","trace_id":"9f2c","msg":"payment timeout","latency_ms":3120}
```

把 trace_id 注入每一条日志，就能从一次慢请求直接跳到它产生的所有日志，这是排查问题最高效的路径。

## 链路追踪

链路追踪（distributed tracing）把一个请求经过的所有服务串成一条 trace，每个服务内部的一段时间叫 span。父 span 与子 span 的嵌套关系，直观地展示了调用拓扑与各段耗时。

1. 入口服务生成 trace_id 并向下透传；
2. 每经过一个服务就新开一个 span，记录开始与结束时点；
3. 采样（sampling）控制开销，通常对错误与慢请求全采，其余按比例采。

指标告诉你「哪里不对」，追踪告诉你「错在哪一步」，日志告诉你「具体是什么值」。三者只有通过一致的关联键（如 trace_id）缝合起来，才真正具备可观测性。

## 小结

不要为了采集而采集。先明确要回答的问题，再倒推需要哪些信号，否则数据只会变成无人问津的存储成本。
