# 无障碍：语义化标签、焦点管理与屏幕阅读器

无障碍（accessibility，常缩写为 a11y）不是给少数人做的额外功能，而是让界面在更多环境下都能工作。键盘用户、屏幕阅读器（screen reader）用户、低视力用户都在日常使用同一套产品，忽略他们，等于主动放弃一部分真实用户。

## 语义化标签

HTML 自带的元素已经携带了角色（role）与状态信息。能用 button 就不要用 div 加点击事件，因为前者天然可聚焦、可被键盘触发、会向辅助技术报告自己是按钮。

- 标题层级按 h1 到 h6 递进，不要为了字号而跳级；
- 用 nav、main、aside 标注区域，屏幕阅读器可以据此快速跳转；
- 表单元素用 label 关联，placeholder 不能替代 label。

| 反例 | 更好的写法 | 原因 |
| --- | --- | --- |
| div 点击 | button | 可聚焦、有语义 |
| 图片无 alt | alt 描述内容 | 读屏可理解 |
| 仅用颜色提示 | 加图标与文字 | 色觉障碍可辨 |

## 焦点管理

焦点（focus）是键盘用户的「鼠标位置」。任何一个操作之后，焦点落在哪里，直接决定用户下一步能不能顺利继续。

> 焦点移走却不告知，等于把键盘用户丢在一条没有路标的路上。

打开对话框时要把焦点移入其中，并把 Tab 限制在弹窗内部（focus trap）；关闭时则要把焦点还给触发它的那个按钮。千万不要用 `outline: none` 粗暴地移除焦点样式，那会让键盘用户彻底迷失，正确做法是替换成更明显的自定义样式。对于单页应用，路由切换后应主动把焦点移回主标题，让读屏用户感知到页面已更新。

## 动态内容的通知

异步更新的内容不会自动被读屏播报，需要使用 ARIA 的 live region。

1. `aria-live="polite"` 适合结果、提示这类非紧急更新；
2. `aria-live="assertive"` 仅用于错误等必须立刻打断的场景；
3. 避免频繁触发，防止读屏被无意义的噪音淹没。

同时也要提供「跳过导航」链接，让用户能绕过重复的菜单直达正文。对于复杂组件，ARIA 只是补丁，优先还是找语义完整的原生元素；一旦用了 `role`，就必须补齐它要求的全部 aria 属性，半吊子的角色往往比不用更糟。

## 测试与协作

无障碍问题最好在开发阶段就发现：自动化审计工具能拦住对比度、缺失 alt 这类显性问题，但键盘操作与读屏体验仍需人工走查。把「只用键盘能否完成核心流程」纳入验收清单，是成本最低、收益最高的一条实践。

## 对比度与缩放

低视力用户会放大页面、调高对比度，因此布局必须能在 200% 缩放下不出现横向滚动，文字也要有足够的对比度。不要用图片承载关键信息，也不要用固定高度裁掉放大的文本。

- 正文对比度至少达到 AA 级要求；
- 仅靠键盘就能完成核心流程；
- 尊重用户的「减少动态效果」系统偏好。

## 小结

语义是地基，焦点是导航，通知是反馈。三者做到位，无障碍就不再是发布前的补救项，而是设计的一部分。
