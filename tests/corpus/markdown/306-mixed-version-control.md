# 版本控制：分支策略、变基与合并、代码评审

版本控制（version control）表面上是记录diff，本质上是在回答一个协作问题：多个开发者如何安全地共享同一份演进中的代码。Git 只提供了机制，而分支策略（branching strategy）决定了这套机制被如何使用。

## 分支策略的取舍

主干开发（trunk-based development）要求所有人尽量往 main 上集成，配合特性开关（feature flag）隐藏未完成的功能；而 Git Flow 则用 develop、release、hotfix 等多条长期分支换取明确的发布节奏。

- 主干开发：集成分支短命，冲突小，但要求完善的自动化测试；
- Git Flow：节奏清晰，适合有固定版本号的产品，代价是分支合并负担重；
- 折中方案：短命特性分支加上 env 分支，也是很多团队现在的默认选择。

## 变基还是合并

merge 会保留完整的分支拓扑，rebase 则把提交线性地「搬」到目标分支顶端。二者并没有优劣，只有适用场景。

```bash
git fetch origin
git rebase origin/main
git push --force-with-lease
```

rebase 的黄金法则只有一条：不要对已经被别人拉取过的公共分支做变基，否则历史会被重写，队友的本地仓库会和远端分叉。私有特性分支上做交互式变基（interactive rebase）则非常安全，还能顺手把杂乱的 WIP 提交整理成几条有意义的提交。

| 操作 | 保留拓扑 | 是否改写历史 |
| --- | --- | --- |
| merge | 是 | 否 |
| rebase | 否（线性） | 是 |

## 代码评审

评审（code review）的目标是提高代码质量并传播知识，而不是证明谁对谁错。

> 一条好的评审意见会说明「为什么」，而不仅仅指出「哪里不对」。

提交粒度也会影响评审质量：一个 PR 只做一件事，超过几百行的改动就很难被认真读完。reviewer 侧则要区分阻塞性意见与建议性意见，前者必须解决，后者留给作者自行判断。把 CI 的检查交给机器人做，人工评审就能专注于命名、边界条件与设计意图。

## 提交信息

提交信息（commit message）是留给半年后自己的一份文档。约定式提交（conventional commits）额外带来一个好处：可以据此自动生成 changelog 并推断版本号。

## 钩子与自动化

把重复的检查交给钩子（hook）与流水线：提交前用 pre-commit 跑格式化和 lint，推送后在 CI 上跑完整测试。约定一旦写进自动化，就不再依赖每个人的自觉。

1. pre-commit 只做快速检查，保证秒级反馈；
2. pre-push 或 CI 承担更重的测试；
3. 提交信息检查与 changelog 生成也可以自动完成。

## 小结

分支策略定义协作边界，rebase 与 merge 决定历史形状，评审把控质量门槛。三者共同构成团队每日都在使用的工作流。
