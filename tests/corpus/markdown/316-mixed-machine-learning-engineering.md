# 机器学习工程：特征管道、离线评估与模型上线

机器学习工程（ML engineering）和做实验最大的区别在于：实验关心「最好的那个模型」，而工程关心「每天都能稳定产出足够好的模型」。这中间的差距，几乎全部落在特征管道、离线评估与上线这三段链路上。

## 特征管道

特征管道（feature pipeline）负责把原始数据变成模型可用的张量，同时保证训练与推理两侧逻辑完全一致。训练/服务偏移（training-serving skew）是这条链路上最隐蔽的坑：离线用 SQL 算出的均值，和线上用另一套代码算出的均值，可能因为空值处理不同而差之毫厘，最终让模型表现整体劣化。

- 特征定义只用一份代码，训练与推理共享同一实现；
- 点时间连接（point-in-time join）防止未来信息泄漏到训练集；
- 对类别特征做统一编码，并处理线上未见过的新类别。

| 环节 | 常见问题 | 缓解手段 |
| --- | --- | --- |
| 采集 | 埋点缺失 | 前置校验与告警 |
| 转换 | 逻辑重复 | 共享特征库 |
| 存储 | 线上线下不一致 | 特征存储（feature store） |

## 离线评估

离线评估（offline evaluation）要用足够接近线上的方式切分数据。随机切分在时序场景里几乎必然乐观：模型在训练时已经「见过」未来。

> 评估指标挑得不对，模型就会朝着错误的方向优化，而且优化得越好，线上越糟。

因此时间序列任务常用滚动切分（rolling window），分类任务则要在类别极度不平衡时看 PR 曲线而不是准确率。

## 模型上线

上线的第一步不是开流量，而是影子模式（shadow mode）：让新模型异步接收真实请求并记录预测，但结果不参与决策，从而在零风险下对比新旧表现。

1. 影子流量验证延迟与输出分布；
2. 小比例金丝雀（canary）灰度，观察核心指标；
3. 逐步放量，保留随时回滚到上一版本的能力。

上线之后还要盯住数据漂移（data drift）与概念漂移（concept drift），它们不会立刻让监控报警，却会缓慢地把模型推向失效。定期重训、保留特征快照、对新旧模型做持续对照，是维持长期可用的必要手段。

另外，模型版本同样要纳入版本控制与制品管理：权重文件、预处理代码、配置参数必须能一一对应地复现，否则一次线上事故可能根本查不出是哪个版本引入的。

## 反馈闭环

模型上线不是终点。把线上预测与真实标签持续回收，形成反馈闭环（feedback loop），下一轮训练才有据可依。缺少反馈的系统只能靠定期全量重训勉强维持，遇到分布突变就会措手不及。

1. 记录每次预测的输入与版本，便于事后归因；
2. 用延迟到达的真实标签做在线评估；
3. 指标异常时先怀疑数据，再怀疑模型。

## 小结

管道保证一致性，评估保证方向正确，上线保证可控风险。三件事做实，模型才可能从 notebook 走进生产。
