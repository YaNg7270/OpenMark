# HTTP 缓存：强缓存、协商缓存与 CDN 回源

HTTP 缓存的全部目标可以概括成一句话：尽可能少地让请求真正到达源站。为此，浏览器与 CDN 提供了两层机制——强缓存直接决定「用不用发请求」，协商缓存则决定「发了请求之后能不能少传点数据」。

## 强缓存

强缓存（strong cache）由 `Cache-Control` 或历史遗留的 `Expires` 控制。命中时浏览器根本不会发出网络请求，直接从本地磁盘或内存读取。

```http
HTTP/1.1 200 OK
Cache-Control: public, max-age=31536000, immutable
ETag: "a1b2c3"
```

带 hash 的静态资源适合设置很长的 max-age 并加上 immutable，因为 URL 一旦变化内容就必然变化，不存在「内容变了地址不变」的风险。

| 指令 | 作用 |
| --- | --- |
| max-age | 相对过期秒数 |
| no-cache | 可缓存，但每次都要校验 |
| no-store | 完全不缓存 |
| immutable | 过期前不复校验 |

## 协商缓存

协商缓存（conditional request）在强缓存失效后登场。浏览器带上 `If-None-Match` 或 `If-Modified-Since`，服务端比对后返回 304，响应体为空，只省下了传输体积。

- ETag 基于内容指纹，精度更高，但需要服务端计算；
- Last-Modified 精度只到秒，且对「内容未变但文件被重写」无能为力；
- 二者同时存在时，ETag 的优先级更高。

> 304 不是「没变」的证明，它只是服务端愿意为这次校验背书。

## CDN 回源

CDN 在边缘节点缓存内容，只有未命中时才回源（origin pull）。回源频率过高会让源站压力陡增，因此要合理设置边缘节点的 TTL，并利用 stale-while-revalidate 让过期内容先顶上、后台再异步刷新，兼顾可用性与新鲜度。

发布新版本时，最稳妥的做法是文件名带内容 hash，HTML 入口则设置较短的 max-age 或者 no-cache。这样用户拿到的新 HTML 会指向全新的资源 URL，天然绕开旧缓存，而不会出现半新半旧的错配。

## 缓存键的设计

缓存键（cache key）决定了命中的粒度。把与结果无关的字段放进键里，会让命中率凭空下降；反之把影响结果的字段漏掉，又会返回错误内容。

1. 键必须完整覆盖所有影响输出的输入；
2. 与用户身份相关的响应要加上区分维度，避免串号；
3. 变化频率差异大的资源最好拆进不同的缓存层级。

## 小结

强缓存负责省掉请求，协商缓存负责省掉响应体，CDN 负责把命中的位置推到离用户更近的地方。设计缓存策略时，先给资源分类，再谈具体的头部指令。
