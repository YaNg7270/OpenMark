# 性能剖析：火焰图、内存分配与缓存命中率

性能优化最容易踩的坑，是凭直觉去猜瓶颈。真正有效的做法先测量再动手：采样剖析器（sampling profiler）每隔一小段时间抓一次调用栈，把这些样本聚合成火焰图（flame graph），一眼就能看出哪些函数占据了绝大部分 CPU 时间。

## 如何读火焰图

火焰图的横轴是样本占比而非时间，越宽的栈帧说明消耗越多；纵轴是调用深度，父帧在下、子帧在上。

- 顶部收窄的「尖峰」通常是叶子函数本身的耗时；
- 中间某层突然变宽，说明问题出在这一层的循环或分配上；
- 出现平台状的宽块，往往意味着阻塞 I/O 或锁竞争。

> 火焰图不会撒谎，它只统计你真正执行过的代码，而不是你以为会执行的代码。

## 内存分配

在很多 GC 语言里，CPU 热点其实来自分配（allocation）。频繁创建短命对象会让年轻代（young generation）不断被填满，触发 minor GC，进而消耗可观的 CPU。

| 症状 | 可能原因 | 对策 |
| --- | --- | --- |
| 分配速率高 | 循环内构造对象 | 复用缓冲、对象池 |
| GC 停顿抖动 | 大对象进老年代 | 降低单次分配峰值 |
| RSS 持续上涨 | 缓存无上限 | 引入 LRU 淘汰 |

把每次请求都要用的临时缓冲区提升到请求级别复用，往往能立刻削掉一大块分配热点。

## 缓存命中率

缓存（cache）的收益完全取决于命中率（hit ratio），而不是缓存本身的容量。

```text
命中率 = 命中次数 / (命中次数 + 未命中次数)
```

如果命中率长期低于某个阈值，那么缓存反而增加了复杂度却没带来收益。真正要优化的是访问模式：把随机访问改造成局部性更强（locality）的顺序访问，让数据尽量待在 CPU cache line 或者 app-level cache 里。对于多级缓存，还要关注一致性——失效策略选错，用户看到的可能比不加缓存更糟。

评估缓存效果时，别只看平均值，一定要看尾延迟（tail latency）：P99 的突变常常来自缓存击穿或雪崩。给热点 key 加上过期时间抖动（jitter），再配合单飞（singleflight）去重，可以在不损失命中率的前提下压平毛刺。

## 压测与基准

剖析找到热点之后，还需要基准测试（benchmark）来验证优化是否真的有效。基准要在稳定的环境里重复多次，关注中位数与尾部的差异，而不是一次跑出来的最好成绩。

- 固定输入规模与硬件，避免结果不可比；
- 用预热（warmup）排除 JIT 编译带来的首轮偏差；
- 记录版本与配置，让结论可以被复现。

## 小结

火焰图找热点，分配统计找浪费，命中率找无效缓存。三步走完，再决定是否值得为性能重构。
