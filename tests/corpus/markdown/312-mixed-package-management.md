# 包管理：依赖树、锁文件与语义化版本

包管理器（package manager）看似只是装依赖，实际上它在解决一个图论问题：如何为成千上万个包找到一组互相兼容的版本。理解依赖树（dependency tree）、锁文件（lockfile）和语义化版本（semver）这三件事，大多数「今天还好好的，明天就装不上了」的问题都能提前避免。

## 依赖树与扁平化

依赖有两种：直接依赖写在 manifest 里，间接依赖则由依赖的依赖引入。理想情况下整棵树是一棵有向无环图，但现实中同一个包的不同版本经常同时出现。

- 若各版本彼此兼容，管理器会提升（hoist）一份到顶层复用；
- 若版本冲突且语义不兼容，只能嵌套安装多份副本；
- 嵌套越深，产物体积和加载路径就越不可控。

| 概念 | 含义 | 存放位置 |
| --- | --- | --- |
| dependencies | 运行时必需 | manifest |
| devDependencies | 仅开发期需要 | manifest |
| peerDependencies | 由使用方提供 | manifest |

## 锁文件的重要性

锁文件把整棵树的精确版本和完整性校验和固定下来，保证 CI 与本地装出完全一致的依赖。

> 没有锁文件的构建是薛定谔的构建：不打开仓库，谁也不知道会装出什么。

在持续集成里务必使用 `npm ci` 这类严格按锁文件安装的命令，而不是会顺带更新锁文件的普通 install，否则锁文件会在流水线上被悄悄改写，掩盖版本漂移。

## 语义化版本

语义化版本约定 `MAJOR.MINOR.PATCH`：主版本号在出现不兼容变更时递增，次版本号在新增向下兼容功能时递增，修订号在修 bug 时递增。

```json
{
  "dependencies": {
    "left-pad": "^1.2.3",
    "toolkit": "~2.0.1"
  }
}
```

前缀 `^` 允许次版本与修订号变动，`~` 只允许修订号变动。很多人默认 `^` 是安全的，但这建立在「维护者严格遵守 semver」的假设上，而现实里主版本不变却引入破坏性改动的情况并不罕见。因此对关键依赖，我更倾向于手动锁定精确版本，再通过定期升级来保持新鲜度。

依赖收敛也是门功课：同一棵子树里出现三四个不同大版本的同一个库，往往意味着构建产物里塞了好几份几乎相同的代码。用 dedupe 和 overrides 主动把它们对齐，可以显著改善体积与调试体验。

## 小结

依赖树决定装了什么，锁文件决定装的是哪一份，semver 决定升级时会发生什么。把三者管好，依赖才能从负债变成资产。
