# 构建工具：打包、代码分割与 tree shaking

现代构建工具（build tooling）要同时满足三个互相拉扯的目标：产物小、构建快、开发时热更新稳。理解打包（bundling）、代码分割（code splitting）与 tree shaking 之间的关系，才能根据项目阶段做出合适的取舍。

## 打包做了什么

打包器从入口（entry）出发，沿依赖图把一个个模块拼接成较少的 chunk，从而减少浏览器要发起的请求数量。

```js
// 入口文件
import { render } from "./render";
import "./styles.css";

render(document.getElementById("root"));
```

除了拼接，打包器还要处理模块格式转换、资源内联、路径重写，以及生产构建下的压缩与混淆。

## 代码分割

当单体产物太大时，首屏下载会明显变慢。代码分割把产物拆成多个 chunk，按需加载。

- 路由级分割：每个页面一个 chunk，进入路由时才拉取；
- 组件级分割：把体积大的编辑器、图表库延迟到真正显示时再加载；
- 动态导入：用 import() 触发一次异步 chunk 请求。

| 策略 | 收益 | 代价 |
| --- | --- | --- |
| 路由分割 | 首屏显著变小 | 切换路由有水合延迟 |
| 组件分割 | 精确按需 | 拆得太碎会变慢 |
| 不分割 | 简单 | 首屏包体过大 |

拆分的粒度并非越细越好，过多的 chunk 会带来额外的请求开销与解析成本。

## tree shaking

tree shaking 依赖 ES module 的静态结构：import 与 export 在编译期就能确定，因此没有用到的导出可以被安全剔除。它有一个常见前提——被引入的模块必须「无副作用」，否则打包器不敢删。

> 一个被标记为 sideEffects 为真的模块，会让整条引入链都变得难以裁剪。

实践中的几个建议：

1. 库尽量发布 ESM 格式，并如实标注 sideEffects 字段；
2. 优先具名导入，避免整包引入后又只用一个函数；
3. 用产物分析工具（bundle analyzer）确认哪些依赖真的进了最终包。

## 构建缓存

构建速度最终要靠缓存来兜底：持久化缓存（persistent cache）会记住每个模块的编译结果，只要内容未变就直接复用。但缓存失效判断一旦出错，就会出现「改了代码产物却没更新」的诡异现象，因此缓存键必须完整覆盖环境变量、编译器版本和配置。

## 小结

打包决定产物形态，分割决定加载时机，tree shaking 决定被淘汰的死代码。三者配合得好，才能让构建既小又快又稳。
