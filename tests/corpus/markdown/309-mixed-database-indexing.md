# 数据库索引：B+ 树、最左前缀与覆盖索引

数据库索引（index）的本质，是用额外的存储空间和写入成本，换取查询时的更低 I/O。理解它为什么是 B+ 树而不是二叉树，是理解后续所有索引规则的前提。

## 为什么是 B+ 树

磁盘按页（page）读写，一次随机 I/O 的成本远高于一次顺序读取。B+ 树的每个节点可以容纳几百个键，这使得树高通常只有三到四层，任意一个键最多三四次 I/O 就能定位。

- 所有数据都存放在叶子节点，内部节点只负责导航；
- 叶子节点之间用链表相连，非常适合范围扫描；
- 由于高度平衡，最坏查找复杂度稳定在 O(log n)。

> 索引不是免费的午餐：它让读变快，却让每一次写都多维护一棵树。

## 联合索引与最左前缀

联合索引（composite index）的键是有序排列的，正因为有序，才能被最左前缀（leftmost prefix）规则利用。

| 查询条件 | 能否用 (a, b, c) 索引 |
| --- | --- |
| WHERE a = ? | 能 |
| WHERE a = ? AND b = ? | 能 |
| WHERE b = ? | 不能（跳过 a） |
| WHERE a = ? AND c = ? | 只能用到 a |

规则本身很直观：把索引想象成先按 a 排序、a 相同时再按 b 排序的电话簿，只翻 b 那一列自然无从下手。范围条件会把后续列「截断」——一旦 b 用了 `>`，c 就无法再用于定位。

## 覆盖索引

覆盖索引（covering index）指查询所需的所有列都出现在索引里，从而无需回表（avoid table lookup）。

```sql
-- 若存在 (user_id, created_at, amount) 的联合索引
SELECT created_at, amount
FROM orders
WHERE user_id = 42
ORDER BY created_at DESC
LIMIT 20;
```

这条查询可以完全在索引上完成，既省去了回表，又因为索引本身有序而跳过了 filesort。代价是索引更宽、写入更重，因此覆盖索引适合那些高频且列数不多的读路径。

需要留意的反面情形是索引失效：对索引列使用函数、隐式类型转换、以 `%` 开头的模糊匹配，都会让优化器放弃索引而退化为全表扫描。上线前用 EXPLAIN 看一眼执行计划，比事后救火划算得多。

## 小结

B+ 树解释了「为什么快」，最左前缀解释了「怎么用」，覆盖索引解释了「怎么更快」。把这三条串起来，索引设计就不再靠运气。
