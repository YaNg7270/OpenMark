# 测试策略：单元测试、集成测试与测试金字塔

测试策略（testing strategy）要回答的不是「要不要写测试」，而是「在哪一层写、写多少」。把所有验证都堆到端到端测试上，回归会慢到没人愿意跑；反过来只写单元测试，又会漏掉组件之间真实的接线错误。

## 测试金字塔

金字塔模型（test pyramid）主张大部分用例落在单元层，少部分落在集成层，最顶端只保留少量端到端用例。

- 单元测试（unit test）：快、稳定、定位精确，但不覆盖真实依赖；
- 集成测试（integration test）：验证模块之间的契约，跑得稍慢；
- 端到端测试（end-to-end test）：最接近用户视角，却也最脆弱。

| 层级 | 数量占比 | 运行时间 | 主要风险 |
| --- | --- | --- | --- |
| 单元 | 约 70% | 毫秒级 | 测不到协作 |
| 集成 | 约 20% | 秒级 | 依赖不稳定 |
| 端到端 | 约 10% | 分钟级 | 偶发失败 |

## 什么样的单元测试才值得写

值得写的单元测试通常围绕「有分支的纯逻辑」：解析器、状态机、金额计算、权限判定。

```ts
import { describe, it, expect } from "vitest";

describe("parseMoney", () => {
  it("rejects negative amounts", () => {
    expect(() => parseMoney("-3")).toThrow();
  });
});
```

而对于薄薄一层胶水代码，写测试的收益往往低于维护成本。测试替身（test double）也有讲究：stub 返回固定值、mock 断言交互、fake 则是一份轻量可用实现。能用 fake 就别用 mock，因为对实现细节的断言会让重构寸步难行。

> 测试应该验证行为，而不是验证实现；否则重构的第一天，测试就会集体变红。

## 覆盖率与信心

覆盖率（coverage）是一个有用的信号，却不是目标。行覆盖率高、分支覆盖率为零，往往意味着大量路径从未被真正执行。相比数字，更该追问的是：核心链路的失败分支有没有被测到？

对于集成层，我倾向于用真实的数据库容器而不是内存替身，因为 SQL 方言与事务语义的差异，恰恰是最容易出问题的地方。端到端测试则要保持精简，只覆盖登录、下单这类最关键的黄金路径（golden path）。

## 小结

金字塔的价值在于指导资源分配，而不是规定精确比例。让快的测试承担广度，让慢的测试守住关键路径，才是可持续的策略。
